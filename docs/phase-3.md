# Phase 3 Implementation Report — Project & Team Management System

## Phase 3 Objective
Migrate Project Management from Phase 1 mock/localStorage storage to a production-grade MongoDB and Mongoose backend with resource-level authorization, member and manager assignments, collision-safe project code generation, search/pagination, and archive capabilities.

Strict Phase Boundary: Projects and Users are now 100% database-backed in MongoDB. Tasks, task dependencies, and task progress remain mock/localStorage driven, pending Phase 4.

---

## Architecture & Relationships

```
MongoDB Data Models:
+-------------------+             +----------------------------------+
|       User        | 1 (manager) |             Project              |
|-------------------|-------------|----------------------------------|
| _id (ObjectId)    |<------------| _id (ObjectId)                   |
| name              |             | name                             |
| email             | N (members) | code (Unique PRJ-XXXX)           |
| role              |<------------| manager (ref: User)              |
| department        |             | members ([ref: User])            |
| status            | 1 (creator) | createdBy (ref: User)            |
+-------------------+<------------| status (PLANNING, ACTIVE, ...)   |
                                  | priority (LOW, MEDIUM, HIGH, ...) |
                                  | category, budget                 |
                                  | startDate, dueDate, archivedAt   |
                                  +----------------------------------+
```

### Relational Schema Definition
- **1-to-Many (Manager to Projects)**: A User with role `ADMIN` or `PROJECT_MANAGER` can lead multiple Projects (`Project.manager -> User._id`).
- **Many-to-Many (Members to Projects)**: Multiple active Users can belong to a Project, and a User can belong to multiple Projects (`Project.members[] -> [User._id]`).
- **Audit Lineage**: `Project.createdBy -> User._id` tracks creation provenance directly from authenticated `req.user`.

## Project Code Generation Strategy
- Automatic code format: `PRJ-XXXX` (zero-padded 4-digit sequence, e.g. `PRJ-0001`, `PRJ-0002`).
- Generated by querying highest numeric suffix via regex `^PRJ-\d+$` and incrementing safely.
- Unique index on `code` enforces database-level integrity against duplicates.

---

## Member & Manager Management Rules
1. **Manager Membership**: A project's manager is automatically guaranteed membership in `project.members`.
2. **Manager Reassignment**: Only `ADMIN` can reassign managers. The new manager must exist, be `ACTIVE`, and have role `ADMIN` or `PROJECT_MANAGER`. The new manager is immediately added to `project.members`.
3. **Manager Removal Protection**: Removing a user who is the active project manager from `project.members` is rejected with `400 Bad Request` unless the manager is reassigned first.
4. **Member Validation**: Only `ACTIVE` users can be added. Adding a duplicate member is rejected with `409 Conflict`.

---

## Soft Deletion / Archive Strategy
- Physical deletion (`deleteOne`/`deleteMany`) is avoided to protect project audit history and downstream data linkages.
- Archiving sets `status = 'ARCHIVED'` and populates `archivedAt = new Date()`.
- Default listings omit archived projects unless query explicitly specifies `includeArchived=true` or `status=ARCHIVED`.

---

## Hybrid Project / Task Compatibility Strategy
- **MongoDB Projects**: Real primary keys (`_id`) with unique human codes (`PRJ-0001`, `PRJ-0002`, etc.).
- **Mock Tasks**: Retain legacy string references (`projectId: 'proj-1'`, `'proj-2'`).
- **Compatibility Bridge**:
  - `normalizeProject()` assigns `legacyId` (`PRJ-0001` <-> `proj-1`).
  - `getProjectTasks(projectId)` resolves tasks by comparing `t.projectId === projectId || t.projectId === project.legacyId || t.projectName === project.name`.
  - Ensures existing task dependencies, overdue flags, and progress sliders continue functioning without modifying Phase 1 task logic.
